# Data contracts and safety

`src/data/units.json` follows the verified Unit order. `exercises.json` follows the Speaking activity order within each Unit. `book.json` stores identity, evidence and scope. `exercise.schema.json` documents exercise fields. The authoritative bank is loaded only from these files (or the generated embedded equivalent); importing progress cannot replace it.

Browser storage key: **english11-speaking.user-data.v1**. A single validated JSON value holds `{version, prefs, phrases, cards}`. A backup wraps it in `{format: "english11-speaking-progress", version: 1, exportedAt, user}`. See `progress.schema.json` and the stricter cross-field checks in `src/progress.js`.

Limits: **4 MiB** UTF-8 per import and stored snapshot; **1,000 phrases**, **3,000 cards**, **100 draft rows per phrase**. IDs are unique ASCII letters/digits/underscore/hyphen, 1–100 characters. Phrase topics allow 200 characters; content fields allow 10,000 characters. Required phrase English and complete card faces must be nonblank. Dates must be real calendar dates; schedule timestamps use canonical UTC ISO timestamps. Preferences reference known Units and exercise IDs and valid Speaking activity/question positions. Unknown object fields, duplicate IDs, invalid schedules and dangling/mismatched links are rejected.

A phrase is `{id,date,topic,english,meaning,reply,drafts}`. Each draft is `{id,front,back,cardId}`; stable draft IDs survive visual row changes. A card is `{id,front,back,createdAt,updatedAt,schedule}`. The schedule stores `{stage,step,interval,ease,reps,lapses,due}`. All times display in the learner browser's locale/timezone; new phrase dates use its local calendar date.

A phrase Save performs card creation/updates and phrase saving in one storage write, after validation. Both blank faces create no card; incomplete pairs remain editable but create no card and report a skipped count. Normalized duplicate pairs use Unicode NFKC, trimmed/collapsed whitespace and lowercase comparison. Shared card edits detach into a new card rather than overwrite another source. Existing non-shared linked edits preserve schedules. Deck edits update all linked drafts. Removing rows or phrases retains cards. Card deletion explicitly clears links. Only Reset schedule resets progress.

Every mutation starts with the latest stored snapshot. Browser Web Locks serialize writes across tabs when available. The fallback is a synchronous latest-read/modify/write with no asynchronous gap, but browsers without Web Locks cannot guarantee serialization of truly simultaneous writes in different processes. No remote synchronization is performed. A stale open phrase editor merges unchanged card draft content from the latest snapshot before saving, preserving concurrent deck edits and ratings.

Restore is validated fully before one replacing write, with an explicit preview/confirmation. Failed durable restores keep the current snapshot. Regular storage failures switch visibly to session-only memory and preserve Download Progress. When initial storage is invalid, the app avoids overwriting it and also enters session-only mode. All learner content is inserted with text nodes or input values; it is never interpreted as HTML. Progress files are local personal data; download before clearing browser data or moving devices.

The optional v1 preference `prefs.hintLevel` accepts `guided`, `starters` or `meaning`. Missing values in existing storage/backups migrate in memory to `meaning`; loading does not rewrite the old snapshot. New saves and exports include the preference. Revealed keyword, sentence-phrase and meaning-hint states are temporary and reset on question or support-level changes. This preference never changes card schedules.

Each exercise now includes an authored `scaffold` with `keywords` (in exact occurrence order in its model), `frame` (sentence starters with ellipses), `frameAnswers` (one exact phrase per ellipsis), and `origin: "authored"`. Keyword splitting retains every other character of the illustrative model. These are local learning supports, not textbook quotations. The Vietnamese meaning hint stays visible in Guided answer and Sentence starters. Meaning only conceals it behind Show meaning hint. Each sentence-starter ellipsis is a separate reveal/hide button; filling every slot reconstructs the exact illustrative model. The prompt allowlist includes a masked speaking pattern only for Guided answer and Sentence starters. It copies literal connecting text plus numbered empty gaps, excluding keyword values, phrase answers and full model answers. Meaning only sends no English pattern. The selected mode and matching Voice instructions are copied explicitly; changing the website does not modify an existing ChatGPT conversation.

## Activity-based practice and migration

Each Unit declares its source Speaking activities in `activities`: stable `id`, source `task`, concise `title`, `titleOrigin: "authored"`, and printed/PDF page references. The 39 activities group all 87 exercises by the leading task number in `exercise.source.task` (so 1a, 1b and 1.1 remain within Speaking 1). These titles are navigation labels, not claimed textbook quotations.

Canonical preferences store `{section,mode,unitId,activityId,index,customIds,hintLevel}`. Daily pools contain exactly one source activity. Custom pools contain exactly the applied selected IDs, ordered by the authoritative bank. The one Copy Voice prompt button copies that whole visible scope and selected support mode; question count is descriptive only. The preview includes every copied exercise in the same order.

Legacy v1 files and browser snapshots containing `lesson` and `index` are validated before conversion. For Daily, the old lesson/index first identifies its exact exercise; migration then finds that exercise's activity and position. Custom keeps its applied IDs, index and support and maps the remembered Daily lesson to its first source activity. Personal phrases, stable draft/card links, full card schedules and all other data are retained. Invalid legacy positions are rejected; they are not clamped into a valid-looking position. Migration happens in memory without an unsolicited storage write, and the next explicit save/export uses `activityId` instead of `lesson`. Use the updated application to read these new activity-based backups.
